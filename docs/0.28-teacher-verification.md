# 教师学籍信息核验方案探索（需求六，2026-08-13）

> 目标：合法、简单地让教师注册者提供学籍信息并完成核验。回答三个问题：
> 需要什么材料？能依赖什么数据库 / API 去验证？单单学信网够吗？

## 一、先界定「学籍信息」指什么

本平台是上财学生创立的家教平台，教师主体大概率是**在读大学生**。因此「学籍信息」= **当前在读状态**（在哪所学校、什么学历层次、是否在读），与已毕业者的「学历证书」是两回事：

| 类型 | 对应官方凭证 | 权威来源 |
|---|---|---|
| 在读学籍 | 《教育部学籍在线验证报告》 | 学信网（www.chsi.com.cn） |
| 已毕业学历 | 《学历证书电子注册备案表》 | 学信网（同源） |
| 学位 | 《学位在线验证报告》 | 学位网（学信网旗下，已并入） |
| 教师资格 | 《教师资格证》 | 教育部教师资格认定中心 |

**结论：学信网学籍在线验证报告是学籍核验的权威单源，且免费。**

## 二、需要教师提供什么材料（MVP 清单）

1. **学信网《教育部学籍在线验证报告》的在线验证码**（12/16 位）+ 报告截图/PDF（可选，用于人工快速比对）。
   - 教师登录学信网 →「学籍查询」→ 申请在线验证报告（免费，2018 年起免费）→ 获得验证码。
   - 验证码有效期默认最长 180 天，可续期 1-6 个月；有效期内可多次核验。
2. **身份证件实名信息**（姓名 + 身份证号），用于把「报告」绑定到「具体的人」。
   - 学籍报告本身不含身份证号匹配（报告显示姓名/学校/专业/学历层次/入学年份）。
   - 需要另行核验身份，防止「拿别人报告冒充」。
3. 可选加分项：学生证照片、在读证明（校务系统截图）、教师资格证。

## 三、核验通道（按成本与合规排序）

### 方案 A：学信网在线验证码核验（免费 · 官方 · 人工/半自动）——**推荐 MVP**
- 教师在平台提交验证码（+姓名），管理员凭验证码到学信网官方核验页
  `https://www.chsi.com.cn/xlcx/bgcx.jsp` 或「学信网报告在线验证」微信小程序扫码核验。
- 核验结果与报告展示信息（姓名/学校/专业/在读状态）与教师自述比对一致 → 通过。
- **学信网官方明确：须用官方小程序/官网核验，不适用第三方扫描**——所以这一步天然是官方通道。
- 成本：0。合规：信息主体（教师）自行申请、自行提供，平台仅核验官方结果，符合最小必要。
- 局限：人工核验有工作量；无法程序化批量验证（学信网无公开 API）。

### 方案 B：机构级学历/学籍核验 API（教育部签约 · 百万级年费）——**不现实**
- 学信网/教育部存在机构级 API（建设银行采购文件实证），但需签约合作，**年费接近七位数**，
  面向大型金融机构/政府单位。对平台当前体量不现实。

### 方案 C：第三方学历核验 API（姓名+身份证 → 学历信息）——**量产期自动化选项**
- 多家合规服务商（数据源自官方授权/国家许可通道）：
  - 天远 API：学历信息查询/学历资质智能核验模型，**约 ¥4.5/次**；
  - 阿里云市场学历查询接口：**¥16000/次性购买**，限企业认证；
  - 九章数盾、羽山数据、中金支付等：企业实名 + 场景审核 + 授权材料。
- 共性要求：**企业实名认证 + 信息主体单独授权 + 查询事由（如企业背调/用工核验）**，
  返回姓名（脱敏）/学校/专业/学历层次/入学毕业时间/证书编号（脱敏）等。
- 合规要点：委托第三方处理需签委托协议、取得用户同意、按 PIPL 做个人信息保护影响评估；
  只用于合法核验事由，禁止二次销售。
- 适合：平台起量、需要自动化批量核验、且能承受按次成本后接入。

### 方案 D：国家网络身份认证公共服务（网号/网证，2025-07-15 施行）——**身份核验层的更优解**
- 公安部等六部门《国家网络身份认证公共服务管理办法》：用户可用网号/网证完成实名核验，
  **平台不得另行要求提供明文身份证信息**（除法定必需）。
- 网证核验「最小化提供」：仅给平台核验结果，不暴露身份证号明文 → 显著降低敏感信息收集面。
- 适合：把「姓名+身份证号」这一步替换为网证核验，合规成本最低。

## 四、单单学信网够吗？—— 分层回答

**够（学籍真实性），但不完整（身份绑定）。**

- 学籍/学历真实性：**学信网是权威单源，够**。在线验证报告 + 官方核验码 = 无法伪造的官方背书。
- 身份绑定：学籍报告无法自动匹配身份证号，必须叠加一层实名核验（网证/第三方/身份证+授权）。
- 如果平台只需要「证明 TA 是在读学生」，学信网报告 + 人工比对姓名 = 当前最小可行方案。
- 若要「自动化 + 强实名」，需要叠加方案 C（第三方学历 API）或方案 D（网证）。

## 五、合规要点（PIPL）

- 身份证号/身份证照片属**敏感个人信息**（PIPL §28），处理须：单独同意 + 特定目的 + 严格保护 + 事前影响评估（§55-56）。
- 收集前充分告知（§17）：目的/方式/种类/保存期限/撤回方式；不得默认勾选同意。
- 保存期限最短化（§19）：核验完成即删或匿名化，不留存身份证复印件。
- 委托第三方核验（§21）：签委托协议 + 监督 + 禁止转委托。
- 最小必要（§5-6）：只收核验所需字段，优先网证/核验结果而非明文身份证。

## 六、推荐落地路径（分期）

| 阶段 | 方案 | 成本 | 说明 |
|---|---|---|---|
| **MVP（现在）** | 学信网在线验证报告 + 验证码/截图 + 管理员人工核验 | ¥0 | 教师提交验证码+姓名 → 管理员走官方核验页/小程序比对 → 通过打「已认证」徽章（复用现有 teacher_profiles.verified 字段与管理端认证审核流） |
| **中期（起量）** | 接入第三方学历核验 API（天远类 ¥4.5/次）自动化 | 按次计费 | 姓名+身份证（经网证或用户授权）+ 查询事由 → 自动比对报告 → 审核从人工转机器 |
| **远期** | 网证实名 + 第三方核验双通道 | 中 | 用户用网证实名（不暴露身份证明文）+ 学信网报告自动核验 |

## 七、接入架构建议（text-audit 同款「咽喉」模式）

- 新增 `server/credential-audit.js`（学籍核验咽喉）：统一 `verifyEnrollment({ reportCode, realName, school?, idHash? })`
  → 输出 `{ ok, degree, school, major, enrollYear }`；MVP 实现 = 人工核验工单（管理员端确认/驳回），
  未来接第三方 API 只换这一模块的 provider 插拔点（同 otp.js 的模拟 provider 模式）。
- 数据存储：只存核验结论 + 验证码（可再验），**不存身份证号明文**（若走第三方 API 只留脱敏结果）。
- 前端：教师档案加「学籍认证」入口（已有 verified 字段与管理员审核流可复用）——
  输入验证码 + 报告截图上传（复用 uploads 暂存区）→ 提交后管理员核验。
- 展示：教师卡「已认证」徽章（现有机制）。
