# UI 心智原则（User-Mindset Principles）— 经世知途·信息门户平台

> **定位**：用户心智原则文档（AK-C1 产物，2026-08-24）。**每个做 UI/交互基元的 agent 开工前先读本文档**，再读 ADR 0004 组件契约与 `docs/project-new-frontend.md`；本文档回答「**为什么用户会这么期望**」，组件契约回答「**怎么实现**」，蓝图（`docs/新前端需求.md`）回答「**做什么形态**」。
> **来源**：用户 2026-08-24 AK 反馈（auth 浮窗 + 落地页视觉交互打磨）逐条提炼，每条附用户原话依据。原则本身是用户长期形成的操作预期，不随单次设计取舍变更。
> **与既有文档的关系（去重说明）**：
> - **蓝图**（`docs/新前端需求.md`「总体风格」+ 组件详述）：规定组件「长什么样、动效怎么做」——本文档不重复形态描述，只提炼「为什么」并给出落地红线。
> - **组件契约**（`docs/adr/0004-new-frontend-component-contract.md`）：规定 token/组件接口纪律——本文档落地指引只引用其机制（`--gray-*` token、`UiButton` 变体、接口帽），不重写契约。
> - 本文档是**独立可引用的一层**：AK-C2 全站组件排查按本文档 10 条逐项核对组件是否符合用户心智。

## 1. Local-first Feedback — 本地即时反馈

**用户原话依据**：「拼图验证等几秒（验证逻辑塞服务端）→ 浏览器本地完成；拼图未居中……加宽+居中撑满主要部分」（AK-A1a/A2）

**普遍用户心智依据**：用户把「拖滑块拼图」感知为纯视觉/操作动作，不是「向服务器提交」。任何等网络往返的延迟都会让用户以为「自己没对准」而反复重试，进而判定功能坏了。用户期望的是「操作完成 → 立刻有结果」，判定应发生在动作本身所在的那一层。

**落地指引**：
- 纯本地可判定的交互（拼图对齐、输入合法性预检、格式提示）一律本地判定即时反馈，零网络往返；本地判定结果作为提交表单的门禁条件，而非额外请求。
- 需要服务端确认的动作，UI 先给「已受理」的即时态，再异步确认；不得让用户等待网络往返才看到反馈。
- 关联组件：`CaptchaPuzzle.vue`（本地对齐判定 `isPuzzleAligned`）、`useConfirmSubmit.js`（门禁条件）、AK-A1a/A1b。

## 2. Black Is Black — 黑字即黑字

**用户原话依据**：「大按钮聚焦后 SVG 字变灰（文档明确排除的写法——黑字就是黑字，除按钮 S 外无文字聚焦灰化）」（AK-B3）

**普遍用户心智依据**：聚焦/悬停是「提示我可点」的聚焦动效，不是「按钮变灰」。用户已把「黑字」读作「可点击的活元素」；聚焦时字变灰会让用户以为按钮失效或状态异常，破坏「这能点」的稳定预期。文字变灰只该出现在真正的禁用态（不可点），且禁用态应整体呈现不可点（禁用填充/不可聚焦），不是聚焦时变色。

**落地指引**：
- A/A1/B/B1/C/C1 悬停/聚焦时**文字与 SVG 保持黑色**，聚焦动效只体现在背景填充/涟漪（`--gray-15` 扩散），绝不灰化文字。
- 文字灰化仅保留给：禁用态（配合禁用填充/不可聚焦，整体呈现不可点）与按钮 S 变体（S 聚焦灰化）；按钮 S1 为常态灰字下划线链接、聚焦转黑，不属于「聚焦灰化」语义。
- **反模式对照**：N-F6 曾按用户要求给 A/A1/B/B1 文字悬停平滑变 60 度灰（`--gray-60`，200ms），AK-B3 按最新指令反转——文字聚焦保持黑色（按钮 S 除外）；ADR 0004 §1.2 按钮契约表格仍为 N-F6 时代陈旧描述，待后续同步。
- 关联 token：`--ink`（主文字，`--gray-90` 别名）、`--gray-60`（次级文字，**非**聚焦文字）；关联组件 `UiButton.vue`（`isBare`/`isPill` 变体共用黑字）、AK-B3。

## 3. Nested Button, Pill Hit-Area — 内嵌套按钮 = 胶囊形交互区

**用户原话依据**：「'发送验证码'按钮聚焦左直边非胶囊 → 内嵌套按钮统一胶囊交互区」（AK-A4）

**普遍用户心智依据**：嵌在输入框/下拉框内部的按钮，用户视线里它就是「这行组件的一部分」。当聚焦态出现直角直边，用户会产生「这是另一个无关控件」或「样式 bug」的错觉。用户期望组件边界内任何可点元素都沿组件整体轮廓呈现——内部按钮的交互区应与容器同形。

**落地指引**：
- 胶囊形容器内嵌套的按钮（验证码发送钮、下拉 V 形钮）聚焦态沿胶囊轮廓（`border-radius` = 容器高度一半），无方形左直边。
- 内嵌按钮的聚焦框/涟漪不得溢出容器边界。
- 关联组件：`UiCaptchaInput.vue`（发送钮）、`UiComboInput.vue`（V 形）、AK-A4。

## 4. Checkbox = Box + Check, No Stretch — 复选框 = 方框+勾，按钮不伸长

**用户原话依据**：「协议两复选：……左边空方框点击变勾按钮不伸长」（AK-A7）

**普遍用户心智依据**：用户对「复选框」有操作系统级的内置认知——一个固定大小的方框，点击出勾，形态恒定。若勾选时按钮拉长、文字位移，用户会以为是「触发了别的什么动作」（如展开面板），产生误判；且复选框通常出现在表单底部多行并列处，形态变化会破坏整行的静态感。紧凑、恒定形态的方框+勾是用户最省心的读取方式。

**落地指引**：
- 协议/复选类用固定尺寸方框 + 勾（原生 `checkbox` 语义：aria/Space 键盘/`label` 包裹），**选中只变勾，不改变组件宽高**。
- 区分「复选按钮」（选中向右伸长的 `UiCheckButton`）与「复选框」（紧凑不伸长的 `UiCheckbox`）：前者用于选项切换类按钮，后者用于协议确认类勾选，按场景选用，不混用。
- 关联组件：`UiCheckbox.vue`（AK-A7 新增）、`UiCheckButton.vue`、`RegisterPane.vue` 协议行、AK-A7。

## 5. Compact Float — 紧凑排版（压高不压字）

**用户原话依据**：「浮窗不应可滚动、注册/登录紧凑 → 组件高度压扁（字号不变、装字组件降高、行距略缩）」（AK-A12）

**普遍用户心智依据**：用户把认证浮窗感知为「一次性小任务」，期望一眼看完、一屏放完。当浮窗需要滚动才能看到确认按钮，用户会以为是布局坏了，且滚动操作在模态里天然别扭。用户允许「更挤」，不允许「字变小」——字号是阅读底线，压缩只能来自组件自身高度与行距。

**落地指引**：
- 认证浮窗整高 ≤ 视口可完整呈现（垂直轴钉死：确认按钮无需滚动即可见），目标是不出现内部滚动。
- 压缩手段排序：装字组件降高（输入框/按钮高度）→ 行距略缩 → 分区留白收敛；**字号与组件最小可点面积（~40px 触控）不允许牺牲**。
- 移动端真机验证（`100dvh` 动态视口）：URL 栏收缩不引入滚动。
- 关联组件：`AuthModal.vue`/`AuthShell.vue` 排版、`UiModal.vue` 面板、AK-A12。

## 6. Underlined Text = Interactive Link — 下划线文字 = 可交互链接

**用户原话依据**：「'已有账号？去登录'改下划线可交互文字、放标题正下方居中」「'手机/邮箱'交互点改下划线文字'改为邮箱注册/改为手机注册'放在 title 右边」（AK-A9/A14）

**普遍用户心智依据**：用户从浏览器/移动端习得「下划线文字 = 可点链接」这一最古老且零歧义的交互语言。用大按钮/选项卡承载次要的往返切换（去登录、改注册方式），在视觉权重上喧宾夺主，用户要找半天；下划线文字轻量、位置紧贴上下文（标题下方/右侧），用户一看即懂是「切换入口」，且不会误当主行动。

**落地指引**：
- 次要的视图往返切换（登录↔注册、手机↔邮箱）一律用下划线可交互文字，紧贴相关上下文放置（标题正下方居中 / 小 title 右侧），禁用大按钮/选项卡承载。
- 下划线文字统一走按钮变体 S1（文本下划线 + 60 度灰）或等价样式，复用 `--gray-60`/`--ink` token，不另造形态。
- 关联组件：`RegisterPane.vue` 去登录链、`MethodSwitch.vue`/channel 切换、`UiButton.vue` 变体 S1、`m-auth.js`（`HAVE_ACCOUNT` 等文案单源）、AK-A9/A14。

## 7. Field Title, One Air — 小 title 统一留白

**用户原话依据**：「小 title 上下空行不够大（'手机验证码'/'选择身份'）→ 改底层组件」（AK-A8）

**普遍用户心智依据**：字段级小标题（表单里每行字段的说明文字）承担「分组/定位」职能，用户靠它的上下留白把表单读成清晰的字段块。各页面各写各的留白会造成「同一网站两种疏密」的割裂感，用户会感知为「不专业/不统一」。留白节奏属于全局一致性资产，不该由每个字段各自决定。

**落地指引**：
- 字段级小标题的上下留白统一走**底层组件/样式单源**（tokens.css 间距 token + 单一 title 组件或全局类），全站一处改全站生效。
- 各业务页面不得自写小 title 的 margin/line-height 特例；确需业务级差异时经底层组件暴露 prop/变量，不改写样式。
- 关联 token：`--space-*` 间距系统；AK-A8。

## 8. Platform Scrollbar — 平台内置滚动条

**用户原话依据**：「边缘默认滚动条覆盖圆角（左圆右方）→ 写平台内置滚动条」（AK-A11）

**普遍用户心智依据**：系统默认滚动条是「外来物」，会盖在浮窗圆角上露出直角，用户一眼看出「这是没处理过的浏览器默认态」。用户对圆角浮窗有「整体圆润」的形态预期，滚动条是浮窗的一部分就该跟着圆角走。平台内置一条薄、圆角、低调的滚动条，既是视觉统一，也是「这产品打磨过」的信任信号。

**落地指引**：
- 可滚动浮窗（auth/通知/更多/列表）统一用平台内置滚动条样式（薄、圆角、token 化），不得裸露系统默认滚动条破坏圆角。
- 滚动条样式单源（一处定义全站生效），token 跟随亮/暗色主题。
- 关联组件：`UiModal.vue` 面板滚动容器、`NotificationsModal.vue`/更多列表等全部可滚动浮窗、AK-A11。

## 9. Big Button = Client Entry — 大按钮 = 客户端入口

**用户原话依据**：「'已有账号？登录'无存在必要（主页两大大按钮即客户端入口——确认是否只做成了注册入口）」（AK-B1）

**普遍用户心智依据**：用户把落地页两个大按钮理解为「进入两个客户端的门」，不是「注册动作」。门的意思是：已登录 → 直接进对应客户端；未登录 → 走到认证入口（此时才出现注册/登录选择）。若大按钮只做注册、把登录藏起来，回访/已登出用户会找不到回自己账号的路，误以为「只能重新注册」。大按钮承担的是「方向选择」，登录/注册是方向选定后的下一层。

**落地指引**：
- 落地页双大按钮语义 = 客户端入口：已登录 → 跳对应角色默认页（`enter.student`/`enter.teacher` 门禁页）；未登录 → 开认证模态（注册场景 + 顶部去登录切换）。
- 不在落地页另放独立「登录」链接（大按钮即入口，登录是入口后的第二层）。
- 关联组件：`LandingHero.vue`（`data-cap` 入口动作）、`openIdentityAuth` 认证模态、AK-B1。

## 10. No Wheel Hijack — 无滚轮劫持

**用户原话依据**：「不要再可用滚轮滚动（N-F5 反转——滚轮劫持致滚到该页滚不下去）」（AK-B4b）

**普遍用户心智依据**：滚轮 = 用户滚动**页面**的通用约定。当可滚动区块（横廊）劫持滚轮做横向滚动，用户在页面该滚的地方滚不动，会立刻判定「页面卡死/坏了」——这是所有劫持中最伤体验的一种。用户能接受在区块上**拖动/触摸**做局部横滚（这是显式的区块内操作），但不能接受滚轮这一全局手势被局部吞掉。

**落地指引**：
- 任何可滚动区块（横廊等）**禁止劫持页面滚轮**（非 passive `wheel` + `preventDefault` 一律不得用于区块内滚动）；滚轮必须滚页面。
- 区块内横向滚动走拖动/触摸手势（`useGalleryDrag` 拖拽、触屏横滑），与页面滚动互不干扰。
- 关联组件：`LandingGallery.vue`、`useGalleryDrag.js`（拖动/触摸横滚）；滚轮劫持逻辑（原 `useGalleryWheel.js`）**已被 AK-B4b 删除**——**反模式对照**：N-F5 曾按用户要求加滚轮劫持，AK-B4b 按最新指令反转——以「不劫持页面滚轮」为定论。
