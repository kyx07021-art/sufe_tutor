## 一、凭证体系演进（短信验证码测试）

### 现状
- 唯一凭证：username + password_hash。users 表凭证列只有 password_hash/salt。
- 登录：/api/auth/login 按 username 查（dbUserLookupStmt），verifyPassword。
- 危险操作二次认证：capToken（danger-ops）。

### 目标
- 公测以手机号为唯一账户凭证；内测把手机号做成基于用户名的增量凭证，方便挂载测试、不动老用户数据。
- 凭证更新做成独立环节（server/credential.js），未来切手机号核心只换凭证更新接口。

### 数据层（A2，users 表 ensureColumns 幂等加列）
```
phone          TEXT  ''      -- 手机号 AES 加密列（可展示，解密出门）
phone_hash     TEXT  ''      -- SHA-256(phone) 可查询列（登录按手机号定位的唯一手段；同 auth_sessions.token_hash）
email          TEXT  ''      -- 邮箱 AES 加密列（账户邮箱，区别于 teacher_profiles.email 授课邮箱）
email_hash     TEXT  ''      -- SHA-256(email)
username_changed_at DATETIME -- 用户名最近修改时间（7 天冷却判定）
```
- 哈希列 + 唯一索引（UNIQUE WHERE 非空）：`CREATE UNIQUE INDEX ... ON users(phone_hash) WHERE phone_hash != ''`。
- AES 密钥走 crypto.bindCryptoEnv（FIELD_ENC_KEY）。

### 验证码咽喉（A3，server/otp.js + verification_codes 表）
成熟方案调研结论（CSDN/掘金 阿里云短信+Redis 防刷、腾讯云短信）：频控、一次性、TTL、发送留痕一起设计。
```
verification_codes(
  id, channel TEXT ('sms'|'email'), target_hash TEXT, code_hash TEXT,
  expires_at DATETIME, used INTEGER DEFAULT 0, created_at DATETIME)
```
- requestOtp(db, { channel, target, req })：
  1. 限频：rate_limits 复用（60s 重发窗口 + 单日上限 + IP 限流，服务端强制——前端倒计时只是表象）
  2. 生成 6 位数字（100000-999999，避免前导零截断）
  3. 存 target_hash/code_hash（验证码哈希存储，不落明文；与 token 同款 tokenDigest）
  4. **provider 插拔点**：OTP_PROVIDER='mock' 时调模拟发送器返回 code（供前端 toast「模拟验证码（内测期使用）」）；生产切真实短信/邮件 API 只改此处，接口签名不变。
- verifyOtp(db, { channel, target, code })：
  1. 按 target_hash 取最新未用验证码，比对 code_hash、校验 TTL（5min）
  2. 一次性：命中即置 used=1（赢家模式 WHERE used=0，防重放并发双消费）
  3. **verifier 插拔点**：内测可接模拟校验器。
- 失败留痕 logEvent（otp.request / otp.verify）。

### 凭证更新独立环节（A4，server/credential.js）
```
updateUsernameCredential(db, userId, newUsername)  -- 改 users.username + 清历史遗留会话（用户名变更即全端令牌作废，防旧名残留）
bindPhoneCredential(db, userId, phone)             -- 写 phone + phone_hash
bindEmailCredential(db, userId, email)             -- 写 email + email_hash
setUsernameChangedAt(db, userId)                   -- 写 username_changed_at=now
getUsernameChangedAt(db, userId)                   -- 读冷却时间
```
未来切手机号为核心凭证：新增 setPhoneAsPrimary 类接口，全平台凭证读取点只改本模块。与「改用户名过程」解耦。

### 接口
- POST /api/user/username { newUsername, capToken }（A5）：requireUser + confirmDangerOtp + 7 天冷却（<7 天返冷却剩余文案）+ 格式校验（不含 @、非纯数字、白名单字符、3-30 位）+ 占用查 → updateUsernameCredential → 返回 ok。用户名变更后旧令牌吊销（credential.js 内），前端 401 自动重登。
- POST /api/auth/phone/send-code { phone } → requestOtp('sms')；POST /api/auth/phone/bind { phone, code }（A6）requireUser + verifyOtp + bindPhoneCredential。
- POST /api/auth/email/send-code / bind 同款（A6）。
- /api/auth/check 扩展（A7）：识别 username/phone/email，返回 { exists, role, kind, bound? }；「不存在的账户」由 exists=false 表达，前端红字。
- POST /api/auth/login 扩展（A7）：identifier 按 kind 定位账户（username 直查 / phone_hash / email_hash），密码校验同现逻辑。
- POST /api/auth/login/code { identifier, code }（A7）：验证码登录——按 kind 定位账户 + verifyOtp + issueAuthToken。

### 前端（B1-B6）
- B1 倒计时组件（app-ui.js）：formatCountdown(ms) 智能单位 + bindCountdown(btn, { endAt, label, onDone })，按钮灰化不可点。
- B2 手机号+验证码组件（app-otp.js 同步层）：固定 +86 前缀（v0.26.15 收敛大陆单区，PHONE_REGIONS 仅 +86，前缀选项连根移除）+ 大陆号格式校验；验证码框内右缘小按钮。
- B3 绑定浮窗（手机号）openPhoneBindModal；邮箱仅设置页入口无浮窗。
- B4 登录页改造（index.html + app-auth.js）：唯一输入框、识别反馈（角色/不存在的账户红字）、密码框/验证码切换、页脚小字。
- B6 模拟验证码 toast。

## 二、滑块拼图真人验证（C）

成熟方案调研结论（极验/腾讯防水墙/通用拼图实现）：**后端生成答案、前端渲染交互、后端校验，归一化偏移上报，一次性 token 防重放**。内测简化。

- C1 app-captcha.js（同步层）：canvas 绘制渐变背景+噪点+随机缺口+滑块；pointer 拖拽；松手比对归一化偏移（offsetX/maxWidth），容差内通过、失败抖动重来。完整动作输出接口 = `openCaptchaModal({ title, onPass })`，onPass 收 { captchaId, offset, track }；注释明确生产接后端 POST /api/captcha/verify（服务端存 cutX、一次性校验），内测接前端 mock 验证器（大差不差即过）。
- C2 withCaptcha(action)：确认按钮点击 → 拦截原请求 → 弹拼图浮窗 → 通过才执行 action。套接点：签约确认、合同签署/取消、修改用户名/手机号/邮箱、注册提交、验证码登录提交。

## 四、高频轻量日常审核通道（E）

成熟方案调研结论（腾讯云/CSDN 海量内容审核架构）：漏斗式多层过滤——词库快速拦截（毫秒）→ AI 打分 → 人工复核；同步审核用于实时场景（IM/弹幕），异步用于展示性内容；降级放行。

- E1 server/audit-flow.js：
  - **监听断点** auditBeforeWrite(path, body, me, req)：内容域写请求统一入口（白名单 /api/posts、/api/student/demands、/api/teacher/profile、/api/reviews、/api/feedbacks、/api/complaints、/api/conversations/*/messages、/api/auth/register、/api/complaints…）。拿数据副本 + 上下文（type/author/ip/body 摘要）入统一队列。
  - **统一信息队列**：内存微队列（当前实例内同步处理，天然「清栈速度远高于堆栈」）；接口注释未来接 Cloudflare Queues/DO 的挂载点。
  - **轻量审核节点** runAudit(item) → { ok, text }。对侧 dummy 组件：默认 ok=true，极小概率（0.1%）返回 { ok:false, text:'dummy审核组件随机驳回一些请求，以测试网站内容审核功能，请再试一次' }。接口留「审核真假值 + 审核组件返回文本」。
  - **300ms 预算**：dummy 同步微秒级天然满足；注释未来 NLP 若超时即 fail-open 放行（不阻塞上传）。
  - **未来设想注释**：dummy → 关键词匹配（Trie/AC 自动机）+ 轻量 NLP 风险评分；打回关键词；放行但风险值高 → 副本另堆长栈（异步队列），定期送高级 API 审核。
  - 驳回/放行留档 audit.*（含 dummy 文本）。
- E2 _worker.js 接入：routeApi 前对内容域写请求跑 auditBeforeWrite，{ ok:false } → 直接返回 400 + text 文案，前端上传过程 catch 自动 toast 原样弹出。
