# 新前端三层并行开发工作流设计

> 版本 v1 · 2026-08-21 · 主会话设计稿
> 适用：经世知途/尼采家教 新前端整体开发（Vue 3 + Vite + SFC，技术栈已定案 AG-2/AG-3/AG-4）
> 配套文档：`docs/project-new-frontend.md`（全局基础文档）、`docs/frontend-decoupling.md`（标准业务接口清单）、`docs/adr/0002-0004`（技术栈/认证路由/组件契约）

---

## 0. 概述

### 0.1 三层角色模型

```
┌─ 第一层 总监督（主会话）─────────────────────────────┐
│  管宏观：拆模块、设基础层、抓模块 agent 的毛病、收口   │
└──────────────────────────┬──────────────────────────┘
                           │ 派发/抽查/验收
      ┌────────────────────┼────────────────────┐
      ▼                    ▼                    ▼
┌────────────┐      ┌────────────┐      ┌────────────┐
│ 模块 agent │  ×10 │ 模块 agent │ ...  │ 模块 agent │  ← 第二层
│  (M0)      │      │  (M-A)     │      │  (M-D)     │    并行写入
└─────┬──────┘      └─────┬──────┘      └─────┬──────┘
      │  每基元派/总结     │                   │
      ▼                   ▼                   ▼
┌──────────────────────────────────────────────────────┐
│ 第三层：idea agent（出方案）× N  ‖ 审计 agent（验收）× 1 │
│  互相不共享上下文；审计与写入解耦                        │
└──────────────────────────────────────────────────────┘
```

### 0.2 三步走总览

| 步骤 | 名称 | 定性 | 产出 |
|---|---|---|---|
| 第一步 | 模块拆分 | **最复杂** | `modules.md`：模块清单 + 依赖矩阵 + 对外接口初版 |
| 第二步 | 基础层设计循环 + 基元拆解 | **工作量最大** | `基础层契约.md`（冻结）+ 每模块 `需求单.md` |
| 第三步 | 并行开发 + 监督验收 + 收口 | **决定成败** | 能跑的业务网站 |

### 0.3 核心设计原则（7 条）

1. **文档即接口**：agent 间通信一律走固化文件（`PROJECT.md` / `基础层契约.md` / 模块`需求单.md` / 实现文档），主会话不逐条搬消息。agent 的第一条指令永远是「读哪个文件」。
2. **第零层先冻结**：基础层是承重墙，先完成、契约测试锁住、所有模块只读。模块间依赖靠冻结切断，否则并行度打成串行。
3. **审计锚定客观标准**：审计 agent 的验收标准锚定「主会话固化的需求单原文 + 项目契约」，不是派发者的转述。审计输入清单固定 = 需求单原文 + 契约 + 实现文档 + 代码，不读写入者的中间讨论。
4. **审计不通过 = 回滚重做**：禁止增量修补（对齐 W29）。审计 FAIL → 回滚该基元 → 重新出方案。
5. **模块内聚、依赖单向、接口最小**：一个模块一个业务域；模块间只依赖显式声明的接口；对外接口越少越好。依赖必须无环。
6. **上下文小而稳**：每层 agent 只带自己需要的最小上下文；同 agent 前缀稳定（固化文件在 prompt 最前、追加历史在后）；模块 agent 靠 **handoff.md 随做随写 + 定期检查点** 防上下文膨胀（§4.3）。
7. **主会话管交界**：模块管不到的地方（跨模块接口失配、契约统一、全站走查）归主会话，收口阶段主会话全权整合。

## 1. 角色与权限矩阵

| 角色 | 层 | 可写 | 只读 | 禁止 |
|---|---|---|---|---|
| 主会话（总监督） | 1 | 基础层、`modules.md`、`需求单.md` 原文、收口代码 | 全部 | 逐条搬消息、替模块写业务代码 |
| 模块 agent | 2 | 本模块目录内代码、本模块实现文档、本模块 handoff.md | 基础层契约、需求单、PROJECT.md、其他模块的对外接口文档 | 改基础层、改其他模块文件、改需求单原文、单方面改共享接口 |
| idea agent | 3 | 无（只回传方案文本） | 需求单原文 + 基础层契约 + PROJECT.md + 本模块相关接口文档 | 读其他 idea 的方案、写任何文件 |
| 审计 agent | 3 | 无（只回传审计报告） | 需求单原文 + 项目契约 + 实现文档 + 本模块代码 | 读写入者的中间讨论、读其他 idea 方案、写任何文件 |

**共享接口变更纪律**：任何模块要改「基础层契约或已声明的跨模块接口」，必须先向主会话提交接口变更申请（说明影响面），主会话批准后才可改；未经批准改共享面 = 契约违规，立即回滚该 commit 并升级处理。

## 2. 第一步：模块拆分（最复杂）

> 为什么最复杂：边界错了，后面所有并行都错——模块间返工成本随开发推进指数上升。所以这一步宁可慢，边界必须钉死。

### 2.1 输入
- 业务蓝图：页面层级 0/A/B/C（`docs/project-new-frontend.md`）
- 标准业务接口清单（`docs/frontend-decoupling.md`，后端能力全集）
- v2 现有功能对照表（保证新前端能力不遗漏）

### 2.2 拆分规则（5 条，违反即返工）
1. **内聚**：一个模块 = 一个业务域；单次业务改动只触碰一个模块。
2. **对外接口最小**：模块对外暴露的接口（路由注册、事件名、数据形状、data-cap 清单）越少越好；多一个接口 = 多一个未来失配面。
3. **依赖单向且无环**：模块只依赖「基础层 + 显式声明的其他模块接口」；依赖图必须是无环拓扑序。出现环 → 合并模块或把共享部分下沉基础层。
4. **通用件归基础层**：按钮/下拉/表单/卡片骨架等被多模块复用的组件一律放基础层组件库，模块内不放通用组件（防 W6 重复实现）。
5. **页面归属清晰**：页面 = 模块的视图，登录注册页归 M0，认证**机制**归基础层（token 管理/401 兜底/路由守卫），机制与页面分离。

### 2.3 模块清单草案（~10 模块 + 第零层）

| 模块 | 职责 | 主要页面 | 对外接口（初版） |
|---|---|---|---|
| 第零层 基础层 | tokens/组件库/路由/认证机制/store/接口帽/工具 | —（不属于任何模块） | 全部模块依赖 |
| M0 落地页 | 游客 landing + 登录/注册页 | 落地页、登录、注册 | 登录注册动作 |
| M-A 学生端 | 教师广场/我的需求/意向/需求卡 | A1/A2/A3 | 建需求、发意向、看关系入口 |
| M-B 教师端 | 需求广场/我的信息/资料广场/档案 | B1/B2/B3 | 接需求、更新档案 |
| M-C1 关系管理 | 关系列表/连线图 | C1 | 关系数据只读接口 |
| M-C2 会话+签约/合同 | 会话页/气泡/发起签约/起草/签署/结束关系 | C2.1-C2.6 | 会话读写、签约推进、结束关系 |
| M-C3 通知 | 通知列表/侧边栏 | C3 | 通知已读、跳转动作 |
| M-C4 设置/关于/反馈 | 账户/设备管理/注销/关于/反馈单 | C3.1-C3.3 | 设置读写、反馈提交 |
| M-D 管理端 | stats/用户/审核/内容/合同/反馈/邀请码 | 管理端 11 页 | admin 动作、面板数据 |
| M-E 内容社区 | 帖子/公告/广播 | 帖子页 | 帖子 CRUD、公告 |

> 说明：签约/合同并入 M-C2（用户蓝图 C2.4/C2.5 是会话的子动作），消除「会话↔签约」环依赖；若后续签约复杂化，再拆独立模块，届时 C2 只依赖签约的接口。

### 2.4 依赖矩阵（第一版，基础层循环中收敛）

```
基础层 ← 全部模块（唯一公共依赖）
M0  ← 基础层
M-A ← 基础层, M-C2(签约入口), M-C1(关系只读)
M-B ← 基础层, M-C2(接单/签约), M-C1(关系只读)
M-C1 ← 基础层, M-C2(会话状态只读)
M-C2 ← 基础层, M-C1(关系数据只读)
M-C3 ← 基础层, 各模块跳转路由（经路由注册表，无直接 import）
M-C4 ← 基础层
M-D  ← 基础层 + 全部后端 admin 接口（前端模块间零依赖）
M-E  ← 基础层
```

依赖原则：模块间依赖只发生在「有明确业务关联」处；`M-C1 ↔ M-C2` 的相互只读依赖必须设计成**单向接口**（如 C1 提供 `getRelationState`，C2 只读它；C2 提供 `getConversationStatus`，C1 只读它），接口形状在第二步冻结。

### 2.5 产出与验收
- 产出：`modules.md`（模块清单 + 每条职责一句话 + 依赖矩阵 + 每模块对外接口初版 + 验收边界）
- 验收：主会话定稿 + 派一个**只读边界评审 agent**（审模块边界合理性/依赖无环/接口最小，对照拆分规则 5 条）；评审 PASS 才进入第二步。

## 3. 第二步：基础层设计循环（工作量最大）

> 核心思想：基础层是**承重墙**，必须先用所有模块的真实实现方案「荷载测试」它，验证能承载一切，再冻结。不做这一步，后期模块实现撞墙 → 被迫改基础层 → 全站返工，成本比现在高一个数量级。

### 3.1 循环结构（主会话主导）

```
主会话设计基础层 v1（tokens/组件/路由/认证/store/接口帽）
        │
        ▼
对每个模块并行派 idea agent：读基础层 v1 + 本模块需求单，
  设想该模块每个基元的实现方案，逐条标注「基础层能承载 / 缺什么」
        │
        ▼
汇总缺口清单 ──→ 主会话评估：真缺口（全模块共性，补基础层）
        │               vs 模块局部（模块实现文档自解，不补）
        ▼
优化基础层 v2（补真缺口）→ 再跑一轮荷载测试
        │
        ▼
 直到缺口清单为空 → 基础层冻结 + 契约测试锁住 + 版本号
```

### 3.2 循环细节
- **基础层 v1 内容**（主会话写）：设计 token 全表（色阶/几何/动效时长）、组件契约（按钮 A/A1/B/B1、下拉、表单、卡片骨架）、路由表（memory history + 角色门禁）、认证流（token 生命周期/401 兜底/capToken）、共享 store 约定、接口帽（data-cap 清单）、工具函数。
- **荷载测试**：每个模块 agent 的 idea 层把「本模块每个基元的实现方案」过一遍基础层，标注三类结论：①承载（方案可直接落）②缺基元（基础层该有但没有，如缺某组件/某 store 方法）③方案自解（模块局部逻辑，不需要基础层）。**只有 ② 类进缺口清单**。
- **缺口归并**：主会话把各模块的 ② 类汇总，判定真缺口（≥2 模块共性或属基础层职责）vs 伪缺口（单模块偶发，可下沉到该模块或走模块内方案）。真缺口补进基础层，伪缺口退回模块。
- **收敛判据**：一轮荷载测试后真缺口清单为空 + 基础层契约自测（契约测试/archtest 式结构断言）全绿 → 冻结。

### 3.3 基元拆解（在循环中完成，第二层做、第一层把关）

- 模块 agent 在设想实现方案时，同时把本模块需求拆成**基元清单**（对齐 W27：原子变更单类 / 整块回滚不心疼 / 拆解粒度复核）。
- 每基元带：编号、一句话目标、实现方案要点、**验收边界**、依赖的接口契约。
- 产出落文件：每模块一份 `需求单.md`（基元清单 + 验收边界 + 依赖接口）。**需求单原文由主会话固化**，模块 agent 无权改——它是后续审计的客观锚点。
- **拆解把关**：主会话按 W27 抽查每个模块的拆解粒度（太粗 = 回滚滚一片，必须退回去重拆）；抽查结果记录。

### 3.4 冻结与产出
- `基础层契约.md`（冻结版）：tokens 全表 + 组件契约 + 路由表 + 认证流 + store 约定 + 接口帽 + 契约测试锁。加版本号，模块 agent 只读。
- 每模块 `需求单.md`（基元清单，固化）。
- `缺口清单.md`（循环全程记录，冻结后归档备查）。
- 冻结标志：所有模块荷载测试零真缺口 + 契约测试绿 + 主会话签发冻结。

## 4. 第三步：并行开发与监督验收（决定成败）

> 模块 agent 十路并行，每模块内部串行处理基元（模块内串行可接受，全局十个模块并行 ≈ 十个主会话同时在干）。主会话不再逐条写代码，专职监督。

### 4.1 模块内基元执行流（每基元走状态机，见 §7）

```
需求单基元 → 派 idea agent（3 个并行出方案，只读）
        → 模块 agent 总结实现文档（选最优 + 补足 + 钉死契约）
        → 派审计 agent（固定模板 + 需求单原文锚点，见 §6.1）
        → PASS → 模块 agent 翻出实现文档动手写入 + 模块自测
        → FAIL → 回滚该基元 → 重新派 idea（带上轮 FAIL 经验）
```

### 4.2 监督机制（主会话专职）

| 监督项 | 手段 | 频率 |
|---|---|---|
| 契约统一 | 跑全量构建 + 契约测试（结构断言锁基础层） | 每模块每完成 10 基元 |
| 拆解粒度抽查 | 读该模块最近基元的验收边界，对照 W27 | 同左 |
| 跨模块接口对账 | 对照 `modules.md` 接口声明 vs 实际实现，找契约 6 类断线（接口形状失配/事件断线/死 data-cap） | 每模块每完成一批（~30 基元） |
| 高风险基元验收 | 跨模块接口/认证/数据写路径/状态机的基元，主会话亲自审 + 真浏览器实测 | 出现即审 |
| 共享面变更 | 接口变更申请审批（§1） | 出现即审 |
| 模块 agent 健康 | 卡死/循环不收敛 → 升级主会话接管该模块 | 持续 |

### 4.3 模块 agent 交接机制（handoff.md 活文档，防上下文爆）

> 模块 agent 是可替换的——上下文一爆就换一个新的。但「换」必须零信息损失：agent 的工作记忆在对历史里，历史里三类东西代码里没有——①决策与理由（为什么这么设计）②踩坑/FAIL 经验（审计为什么失败）③进行中的未完成状态。交接 = 把这三种持久化成文件。**交接文件是随做随写的活文档，不是「快爆了一次性倒出来」**——劣化状态下回忆必然遗漏，且写交接本身还占上下文。

**handoff.md（每模块一份，`docs/modules/<模块>/handoff.md`）内容 8 项**：
1. **模块元信息**：指向 `modules.md` / `需求单.md`，不重复抄。
2. **基元进度表**：需求单每个基元的状态机位置（pending/…/done/rollback）+ 审计报告路径 + commit。
3. **契约决策记录**：本模块定的接口形状、data-cap 名、事件名、store 用法——**新 agent 必须继承，不能重新发明**（否则交接两批 agent 做出不一致接口 = 契约漂移）。
4. **关键设计决策 = 结论 + 理由**：每条一行，防新 agent 推翻重来。
5. **踩坑 / FAIL 经验**：审计失败原因、基础层缺口 workaround。
6. **进行中未完成**：写到哪、差什么、下一步。
7. **待主会话审批的交互**：未决接口变更申请、跨模块对账项。
8. **下一批起点**：明确「从基元 X 开始做 Y」。

**写入时机（不靠「爆了才写」）**：
- 每完成一个基元 → **增量追加**（进度表 + 新决策 + 新踩坑）。
- 上下文到 ~70% 或每 5-10 基元 / 2-3 小时 → **正式检查点**：确认 handoff 最新 + 写「下一批起点」+ 重开干净 agent 续跑。
- 模块 agent 始终在健康状态下写交接，质量有保证；任何时刻 handoff 都是完整的，最坏情况上下文爆了直接换 agent 零损失。

**新 agent 接手清单**：读 PROJECT.md → 基础层契约 → 模块需求单 → **handoff.md** → 最近完成基元的实现文档/代码 → 从「下一批起点」继续。

**信任模型**：handoff 是**索引 + 上下文补充，不是权威**。权威链 = 审计报告文件（验收状态以文件存在为准，不信 handoff 的「已验收」声明）+ 需求单原文（验收边界）+ 基础层契约 + 已写代码。若新 agent 发现 handoff 与代码矛盾，以代码 + 审计报告为准并上报主会话。

**监督**：新 agent 接手后主会话抽查其是否继承契约决策（有没有重新发明已定接口/data-cap 名）——交接失败的早期信号。

**审计隔离**：审计 agent **不读** handoff.md（它是写入者的记忆，读了会破坏独立性）；审计输入保持固定清单（§6.1）。

**费用**：交接反而有利 DeepSeek 缓存——新 agent 前缀小且稳定；每基元增量写 handoff 的 token 开销远小于上下文爆后的返工。

### 4.4 升级路径

| 情况 | 处理 |
|---|---|
| 模块 agent 审计连续 FAIL ≥2 次同一基元 | 升级主会话：主会话亲自审该基元的需求与基础层承载力，判定是「基元拆错」还是「基础层缺能力」，修正后重走 |
| 模块 agent 卡死/循环 | 主会话接管该模块（读检查点，直接派下一批） |
| 契约违规（偷改基础层/共享接口） | 立即回滚该 commit + 主会话复核该模块全部最近基元 |

## 5. 收口：统一成能跑的业务网站（主会话全权）

1. **全量整合**：构建 + 全量测试 + 契约测试 + lint/结构断言。
2. **跨模块对账**：对照 `modules.md` 与各 `需求单.md`，全站扫三类断线——①import 符号缺失 ②懒加载/时序（readyState/DOMContentLoaded）③跨模块接口形状不一致（前端被迫三元适配）。
3. **契约统一**：data-cap 全站盘点（零 handler = 死 UI）、事件名/路由注册表核对、设计 token 引用一致性。
4. **真浏览器全站走查**：首访新用户视角（无痕）走 落地→浏览→登录→onboarding→业务全链路；几何断言（视口内/不溢出）；移动端视口；零 console/PAGEERROR/CSP 违规。验证脚本必须含被拦路径负用例（点遮罩/点弹窗外页面）。
5. **交界修复**：模块 agent 管不到的跨模块问题（渲染衔接、路由进离场、全局状态）主会话直接修。
6. **交付**：验收三条件（程序合规/功能正常/代码干净）全绿，交付能跑的业务网站。

## 6. 贯穿机制

### 6.1 审计独立性（相对独立，锚定客观标准）

- 审计 agent 的验收标准锚定**主会话固化的需求单原文 + 项目契约**，不是模块 agent 的转述——模块 agent 可能理解偏了基元、可能美化自己的实现文档，但它无权改需求单原文。
- **审计输入固定清单**（缺一不可、多一不可）：①需求单原文（该基元 + 验收边界）②项目契约（基础层契约 + 通用审计契约 A1-G5）③实现文档 ④该模块代码。
- 审计 agent **不读**写入者的中间讨论和内心戏（为什么选这个方案、放弃那个）。
- 审计 prompt 用主会话预制的固定模板，模块 agent 派审计时只能填「审计对象 = 基元 X」和「实现文档路径」，**无权改验收标准**。
- 审计 agent 由模块 agent 派（保持局部自主、不阻塞主会话），但独立性由「锚点文件 + 固定输入 + 固定模板」结构性保证，不依赖派的那个人的自觉。

### 6.2 回滚重做语义

- 审计 FAIL = 验收不通过 = **回滚该基元实现**，禁止增量修补（对齐 W29：不做小修小补，重写干净架构）。
- 回滚后，重新派 idea agent 时把上轮 FAIL 经验写进基元介绍（对齐规则 B/C 的「FAIL 经验补充」）。

### 6.3 文档即接口

- `PROJECT.md`（全局，所有 agent 先读）→ `基础层契约.md`（冻结）→ 模块 `需求单.md`（基元 + 验收边界）→ 实现文档（每基元一份，审计读它）。
- 主会话的裁判结论（选方案/补基础层/批接口变更）一律落文件，不塞 prompt、不逐条搬消息。

### 6.4 上下文与费用控制（DeepSeek 前缀缓存适配）

- DeepSeek 缓存是**前缀逐字节匹配** + 自动 TTL（几小时到几天）：命中要求「本次请求开头与缓存记录逐字节一致」。
- 落地规则：
  1. 固化文件走「agent 自己读文件」，不整份塞 prompt（prompt 只放「读哪个文件 + 一句任务」）。
  2. 同 agent 前缀稳定：同一模块 agent 的连续请求保持「系统提示 + 本模块需求单」在 prompt 最前，追加的历史在末尾；禁止在系统提示里注入易变内容（时间戳/git status 输出）。
  3. 每层上下文小型化：idea/审计只带一个基元；模块 agent 靠检查点控制增长（§4.3）。
  4. 简单基元 idea agent 可降到 1 个（省并行费用），复杂基元 3 个。
- 目标：任何 agent 的连续轮询命中自己的前缀缓存；三层上下文互不干扰属正常（各自独立缓存）。

### 6.5 契约统一（防屎山）

- 基础层冻结 + 契约测试锁（结构断言：tokens 单源、组件单实现、data-cap 零死 UI、零内联事件/样式、路由注册表完整）。
- 模块内零通用组件（通用件必须从基础层 import，W6）。
- 跨模块接口形状变更走审批（§1），禁止前端三元适配绕过（契约 6 类第三类断线）。

## 7. 基元状态机

```
        idea 并行(3)         总结实现文档        派审计（固定模板）
[pending] ──────► [designing] ──────► [documented] ──────► [auditing]
                                                                │
                     ┌──────────────────────────────────────────┤
                     ▼                                          ▼
              [rollback] ◄── FAIL（回滚该基元，带上轮经验重来）   │
                     │                                          │
                     └─────────► [designing]                    │
                                                                │ PASS
                                                                ▼
[done] ◄─ 主会话抽查 ─ [verified] ◄─ 模块自测 ─ [written] ◄─ [accepted]
```

- `pending`：需求单中的基元，待开工。
- `designing`：idea agent 并行出方案。
- `documented`：模块 agent 总结实现文档定稿。
- `auditing`：审计 agent 验收（锚定需求单原文）。
- `accepted`：审计 PASS，待写入。
- `written`：模块 agent 按实现文档写入代码。
- `verified`：模块 agent 模块内自测通过（含变异守护）。
- `done`：主会话抽查通过。
- `rollback`：审计 FAIL 或主会话抽查 FAIL，回滚该基元，重新 design（补充 FAIL 经验）。

## 8. 里程碑与验收

| 里程碑 | 内容 | 完成标志 |
|---|---|---|
| M0 | 模块拆分定稿 | `modules.md` + 边界评审 PASS |
| M1 | 基础层冻结 | 全模块荷载测试零真缺口 + 契约测试绿 + 主会话签发冻结 |
| M2-M11 | 各模块 done | 该模块全部基元 `done` + 主会话抽查通过 |
| M12 | 收口交付 | §5 全项通过，验收三条件全绿 |

**验收三条件（每基元、每模块、最终收口统一适用）**：
1. 程序合规：实现过程没有走捷径违反任意一条工程要求，严格维护架构契约。
2. 功能正常：真实生产环境（浏览器/客户端）验证功能，无预期外表现；验证含被拦路径负用例 + 渲染几何断言。
3. 代码干净：无逻辑 bug，无可能导致屎山的特例/旁路/硬编码。

## 9. 参数建议

| 参数 | 建议值 | 说明 |
|---|---|---|
| 模块 agent 数 | ~10（并行） | 模块数 = 第一步定稿的模块清单 |
| idea agent / 基元 | 复杂 3 / 简单 1 | 够多样性，不浪费费用 |
| 审计 agent / 基元 | 1（必跑） | 固定模板 + 需求单锚点 |

| 模块 agent 正式检查点 | 上下文 ~70% 或 每 5-10 基元 / 2-3 小时 | 确认 handoff 最新 + 写下一批起点 + 重开干净 agent |
| 主会话监督节奏 | 每模块每 10 基元一次全量构建+契约测试+抽查 | 见 §4.2 |
| 跨模块接口变更 | 主会话审批制 | 见 §1 |
| idea/审计 上下文 | < 30k tokens | 只带一个基元 + 锚点文件 |
| 模块 agent 上下文 | < 100k tokens | 超了检查点重开 |

## 10. 风险与对策

| 风险 | 后果 | 对策 |
|---|---|---|
| 模块边界错 | 跨模块返工，成本指数上升 | 第一步主会话定稿 + 边界评审 agent；依赖必须无环 |
| 基础层承载力不足 | 后期撞墙，全站返工 | 第二步荷载测试循环直到零真缺口再冻结；冻结前不开发模块代码 |
| 审计独立性失效（写者自派审计） | 自审自，缺陷漏网 | 验收锚定需求单原文 + 固定输入清单 + 固定模板；模块 agent 无权改验收标准（§6.1） |
| 模块 agent 增量修补 | 特例爆炸、补丁屎山 | 审计 FAIL = 回滚重做（§6.2），禁增量修补 |
| 上下文膨胀 / 缓存全 miss | 费用爆炸、质量劣化 | §6.4：前缀稳定、读文件不塞 prompt、检查点重开、上下文小型化 |
| 交接信息丢失（换 agent 失忆） | 新 agent 重新发明契约 / 推翻决策 / 重复踩坑 | handoff.md 随做随写（每基元追加）+ 正式检查点 + 信任模型（以审计报告/代码为权威）+ 主会话抽查继承性（§4.3） |
| 模块间接口失配 | 收口期断线爆炸 | 接口在第二步冻结 + 主会话审批变更 + 收口期跨模块对账 |
| 模块 agent 卡死/循环 | 局部停摆 | 升级主会话接管（§4.4） |
| 契约漂移（偷改共享面） | 基础层腐坏 | 契约测试锁 + 违规立即回滚 + 复核该模块全部最近基元 |
