# 交付工作流设计方案（Q-10 · 2026-08-20）

本设计定义「保证每次交付质量完美、且以后工作流能直接稳定交付」的标准工作流。它把历轮审计（Z/Q 需求 17 面）与 Q-8 原则契约沉淀的实践**系统化、文档化、固化为可重复执行的标准流程**，不再每次从零发明。

适用范围：本项目所有代码 / 配置 / 文档交付。本设计是现行文档，Q-11 据此执行基元任务单；执行改动入 CLAUDE.md 规则区时按 Q-8 式流程（原则式表述 → 与既有规则去重 → 独立审计）。

## 1. 核心原则（从 Q-8 契约与历轮教训提炼）

| 原则 | 来源 | 承载 |
|---|---|---|

| 验收有牙齿：断言须变异守护 + 负路径 + 几何，不只"不炸" | Q-6 / Z-14-F1/F2 | G2 / W43 / G5 |

## 2. 交付工作流（阶段 0 前置 + 阶段 1-5）

### 阶段 0 · 需求接收与拆解
输入：用户需求。
动作：
1. 立即基元拆解写入 CLAUDE.md（W23 / W24），每条需求单独拆解（W24），禁止批量。
2. 拆解粒度复核 agent（对照 W27 标准逐基元审：整块回滚不心疼 + 验收边界 + 单类变更），复核 PASS 才开工。
3. 验收三条件前置声明（程序合规 / 功能正常 / 代码干净）。
4. 需用户判断或只有用户能完成的操作（如 admin 口令）留最后（W38）。

### 阶段 1 · 实现（主会话）
每基元：取快照（CLAUDE.md 或 git）→ 实现 → 自我验证（W30）→ 独立审计 agent（W31）→ **PASS** 进下一条 / **FAIL** 回滚重做（W29）。禁止增量修补堆补丁。
遵循搭积木配方与项目契约（R-1），数值/文案走单源（P4），副作用纪律（P6）。

### 阶段 2 · 审计（标准审计套件）
按"面"审计：面 = 一类可独立验收的检查单元。**标准审计套件面清单（Z/Q 17 面沉淀）**：
1. 契约行为绕过面（archtest 锁不住的动态绕过技术通道）
2. 认证与网安咽喉面
3. 审核链与危险操作咽喉面
4. 核心业务域面（teacher/demand）
5. 聊天域面
6. 合同与结算域面
7. 管理与支撑域面
8. 数据正确性横切面（schema/迁移/版本门控）
9. 根 server 遗留层面
10. shared 单源面
11. 前端 core 基础层面
12. 前端 core 渲染数据层面（缓存 invalidate 独占）
13. 前端 features 核心域面
14. 前端 features 支撑域面
15. 工具链/部署/资产管线面
16. 测试体系面
17. 真实生产环境验证面

每面派只读 agent 并行扫全栈（W40），报告带证据链 + 严重度（W33）。三层验收边界：**面交付 = 报告定稿**；**面验收 = 报告 + 全部确认 bug 修复基元独立审计 PASS + 全量测试/arch/build/hash-assets 绿**；**修复基元 FAIL → 回滚重做**。
跨面对账归属写死（Z/Q 先例）：契约 6 形态 / 缓存 invalidate / 通知结构化 / SUFE_REGIONS / chat 竞态 / schema 机制，每面报告加「跨面归属」注记。

### 阶段 3 · 回归与验证
- **上线检查清单**（固化顺序，规则 P17/P20）：`node hash-assets.mjs` → `npm test` → `npm run test:arch` → `npm run build` → commit+push（后台重试线程 P16）→ `/api/health` 验线上 → 反馈单巡检（P20）。
- **验证脚本套件**：`verify-csp-strict.mjs`（CSP 三路真拦 + 全链路零违规 + 几何断言）、`verify-captcha-render.mjs`（像素级验证）、`verify-staging-smoke.mjs`（真实部署产物 + Playwright + SPA 回退）。
- **变异守护（G2）**：锁定真实行为的断言做还原验证（还原修复 → 断言变红），不只断言"不炸"。
- **负路径断言（W43）**：验证脚本必须含「用户可能尝试但被拦的路径」负用例（点遮罩 / 点弹窗外 / 点被覆盖元素 / 移动端），不只 happy path。
- **几何断言（G5）**：元素在视口内 / 不溢出，不只 DOM 存在。
- **真实生产验证**：QA 账户（qa_student / qa_teacher）全链路 + 首访新用户心智模型（先模拟新用户首屏，再验证后续操作）。

### 阶段 4 · 发版
- **攒批纪律（P15）**：同一反馈轮内多条小修合并为一次 bump+发版（z +1 一次），禁止逐条小修单独发版 / 发公告；纯内部调整（无用户可见变化）不发公告。
- **公告门控（P18）**：版本探针（轮询等 Pages 激活约 64s）+ 本地自动读 shared/config 版本双匹配，版本不对绝不发。
- **发布清单**：Secrets（如需）→ push（push-retry.sh 后台线程，判成败重定向到文件再判）→ `/api/health` ready → 版本探针逐字一致 → 核心资产全 200 → 生产数据校验（validate-prod-data）→ 公告（announce.sh，格式钉死 P19）→ 反馈单巡检（P20）。

### 阶段 5 · 上线后巡检
- 反馈单巡检（P20）：每次上线新版本后拉一次反馈单；有不在当前任务单里的问题 → 拆新基元任务；已在任务单 → 标记已处理。
- 攒批发版，循环至稳定。

## 3. agent 使用范式

| 角色 | 触发 | 输入 | 输出 | 验收 |
|---|---|---|---|---|
| 拆解粒度复核 agent | 拆解方案写入后 | 拆解方案 + W27 标准 + 验收三条件 | 逐基元粒度复核（不够细继续拆） | 复核 PASS 才开工 |
| 审计 agent（按面） | 面交付时 | 该面范围 + 全部工程要求 + 验收三条件 | 发现清单（证据链 + 严重度 1101/中/轻） | 面交付 = 报告定稿 |
| 修复基元审计 agent | 每个修复 commit | 修复上下文 + 全部工程要求 | 独立验证报告（三条件逐条） | 独立审计 PASS |
| 收口自查 agent | 需求收口 | 验收清单（无重复/零残留/编号无断/分类正确/契约一致） | 全绿报告或 FAIL 清单 | 全绿才收口 |

主会话只做需判断的整合与验收（W40）；审计用只读 agent 并行扫全栈。审计 agent 必给全部上下文与工程要求，禁止省略式派发。

## 4. CLAUDE.md 维护方式

- 规则区只放契约与常量，不含经验教训（文件头已声明）；进度/待办/复盘看 git 历史与会话。
- **新教训 → Q-8 式契约化流程**：教训盘点归桶 → 提炼原则式表述（禁文件名/版本号/事故名）→ 与既有规则去重 → 独立审计 → 写入原则契约章节。不往既有规则里堆单次事故细节。
- 需求单用完即删；交接现状按需求完成情况例行更新（不堆日志）。
- 编号体系：通用 W1-W43、项目 P1-P22、原则契约 A1-G5+B2、架构契约速查 R-1（内部契约 1-10 编号 archtest 锁定不动）。

## 5. 版本纪律

- 版本 x.y.z（P15）：x=1 正式版起；y 大更新/重构 +1 且 z 归零；z 每批小修 +1。commit 必须同 commit 更新 APP_VERSION；公告文案与版本号一致。
- 攒批纪律：同一反馈轮小修合并 bump；纯内部调整不发公告。
- 内容哈希资产管线（P17）：改代码 commit 前必须 `node hash-assets.mjs`，漏跑由 hash-build.test.js 红例兜底拦截。

## 6. 验证深度清单（固化，交付前逐项核对）

1. 三层验收：程序合规 / 功能正常（真实生产环境复现）/ 代码干净
2. 断线三查（W32）：import 符号缺失 / DOM 就绪时序 / 跨模块接口形状
3. 契约行为绕过面：动态绕过技术通道（拼串 / 模板串 / 大小写 / 换行 / fromCharCode）
4. 变异守护（G2）：锁定真实行为的断言还原验证
5. 负路径断言（W43）：被拦路径负用例
6. 几何断言（G5）：元素在视口内 / 不溢出
7. 真实生产验证：QA 全链路 + 首访新用户心智模型
8. CDP 违规捕获：CSP 零违规（三路：console / pageerror / CDP）
9. 数据正确性：validate-prod-data 生产数据校验
10. 反馈单巡检（P20）

## 7. 方案取舍

- **方案 A（本设计）：文档化工作流 + CLAUDE.md 规则承载 + 既有验证脚本套件复用。** 不新造工具链（规则 W2 最简单实现 / W5 复用成熟物）。工作流是"流程纪律"，靠文档+规则+agent 范式保障，不靠额外代码。
- 方案 B（脚本化工具链）：把发布清单/审计套件固化为 shell 脚本。被否——发布清单各步需人工判断（版本探针语义/Secrets/重加密），脚本化引入维护成本与误判面，且 hash-assets/test/arch/build/verify 已有现成命令，缺的是"顺序与核对"而非"执行器"。
- 方案 C（全部契约进 archtest）：只对可断言形态契约（CSP/region/零内联等）入 archtest，流程类纪律（攒批/巡检/审计顺序）不可断言不入。与 A 互补，非替代。
